> 知识阶段：治理与归档  
> 适用范围：`nfs-knowledge-base` 下的所有知识文档、实验记录、案例复盘和附录  
> 版本：1.0.0  
> 生效日期：2026-07-31  
> 前置文档：无  
> 后续文档：所有 `NFS-KB-*` 文档

## 1. 目的与适用范围

本规范定义 NFS 企业级知识库的文档标识、目录、元数据、内容结构、证据要求、版本与归档规则。

目标是让每份文档都能被稳定定位、追溯前置知识、验证技术结论，并可在故障处置或架构评审中直接复用。自本规范生效起，后续新增或修订的 NFS 知识库文档必须遵守本规范。

## 2. 知识库根目录

所有知识库内容存放在：

```text
docs/nfs-knowledge-base/
```

目录结构如下：

```text
nfs-knowledge-base/
├── README.md
├── 00-governance/
│   └── NFS-KB-00-01-document-management-standard.md
├── L0-foundation/
├── L1-protocol/
├── L2-deployment/
├── L3-security/
├── L4-performance/
├── L5-troubleshooting/
├── L6-architecture/
├── L7-practice/
└── appendix/
```

目录归属规则：

| 目录 | 内容边界 |
| --- | --- |
| `00-governance` | 文档规范、术语规范、学习路线与知识库治理记录 |
| `L0-foundation` | Linux VFS、页缓存、网络、RPC/XDR 等 NFS 前置知识 |
| `L1-protocol` | NFSv3、NFSv4.0、v4.1、v4.2 协议与状态模型 |
| `L2-deployment` | 服务端导出、客户端挂载、配置基线与运行维护 |
| `L3-security` | 权限、身份映射、Kerberos、LDAP/AD、SELinux |
| `L4-performance` | 性能模型、压测、监控、调优与容量规划 |
| `L5-troubleshooting` | 故障现象、证据链、根因、恢复与预防 |
| `L6-architecture` | 高可用、容器、灾备、选型与企业架构 |
| `L7-practice` | 综合实验、演练、设计作业与复盘 |
| `appendix` | 命令速查、术语、版本兼容矩阵和参考资料 |

一个文档只归属一个主目录。内容跨多个领域时，按主要问题域归档，并通过“关联文档”链接其他知识点，不重复维护相同结论。

## 3. 文档标识与文件命名

### 3.1 命名格式

所有正式文档使用以下文件名：

```text
NFS-KB-{阶段编号}-{单元编号}-{主题英文标识}.md
```

字段说明：

| 字段 | 格式 | 规则 |
| --- | --- | --- |
| `NFS-KB` | 固定前缀 | 全部大写，不变更 |
| 阶段编号 | `00`、`L0` 至 `L7`、`APP` | 与目录所属知识阶段一致 |
| 单元编号 | 两位数字，如 `01` | 在同一阶段内递增且永久稳定 |
| 主题英文标识 | 小写 kebab-case | 描述主题，不使用空格、中文或版本号 |

示例：

```text
NFS-KB-L0-01-end-to-end-io.md
NFS-KB-L1-02-rpc-xdr-and-compound.md
NFS-KB-L2-03-export-and-mount-strategy.md
NFS-KB-L4-02-performance-benchmark.md
NFS-KB-L5-04-hung-io-troubleshooting.md
NFS-KB-APP-01-command-reference.md
```

### 3.2 编号稳定性

已发布文档的阶段编号、单元编号和文件名不得因插入新主题而重排。新增主题使用下一个可用编号；当需要在既有主题之间扩展时，仍创建新的独立编号，不使用 `01a`、`01-1` 或 `final` 等临时编号。

文档标题应与文件名主题一致，但面向阅读者使用清晰的中文标题。例如，`NFS-KB-L1-02-rpc-xdr-and-compound.md` 的一级标题为：

```markdown
# NFS-KB-L1-02 RPC、XDR 与 COMPOUND 操作
```

## 4. 统一元数据

每份正式文档在一级标题后必须包含以下元数据块：

```markdown
> 文档状态：草稿 | 待验证 | 已验证 | 已归档  
> 知识阶段：L0 基础设施层  
> 适用范围：RHEL 8/9、Rocky Linux 8/9、Ubuntu 22.04/24.04；NFSv3/v4.0/v4.1/v4.2  
> 版本：1.0.0  
> 最后更新：YYYY-MM-DD  
> 前置文档：[NFS-KB-L0-01-end-to-end-io](../L0-foundation/NFS-KB-L0-01-end-to-end-io.md)  
> 关联文档：无
```

规则如下：

| 字段 | 要求 |
| --- | --- |
| 文档状态 | 使用第 7 节定义的受控状态值 |
| 知识阶段 | 写明阶段编号与中文名称 |
| 适用范围 | 写出发行版、内核/NFS 版本或场景边界；不确定时明确“待验证” |
| 版本 | 遵循第 8 节语义化版本规则 |
| 最后更新 | 使用 `YYYY-MM-DD` 格式 |
| 前置文档 | 列出理解本文必须具备的知识；无前置则填“无” |
| 关联文档 | 列出强相关但非前置的文档；无则填“无” |

## 5. 正式文档结构

除治理文档、速查表等特殊类型外，学习单元必须按以下顺序组织：

```markdown
# 文档编号与主题

> 统一元数据

## 目录

## 1. 学习目标与问题边界

## 2. 原理与协议/内核机制

## 3. 端到端流程图

## 4. 配置、命令与参数说明

## 5. Java 工程视角

## 6. 生产实践与风险边界

## 7. 验证实验与观察指标

## 8. 排障线索或检查清单

## 9. 小结

## 10. 参考资料与关联文档

## 变更记录
```

要求：

- 协议、状态机、调用链和因果关系使用 ASCII 图或 Mermaid 图表示；图中的文字必须与正文术语一致。
- 每个核心机制至少提供一个可执行命令、配置片段或最小验证步骤。
- 命令必须标注执行端：`[客户端]`、`[服务端]` 或 `[两端]`。
- 配置示例必须说明适用版本、风险、预期效果及恢复方式。
- 涉及安全敏感项，例如 `no_root_squash`、`insecure`、`async` 和 Kerberos 降级策略时，必须单列“风险边界”，禁止作为无条件推荐项。
- Java 相关主题必须说明 JDK API 行为与 Linux 系统调用/NFS 语义之间的关系；不能仅给出 Java 代码而不解释文件系统语义。

## 6. 实验、结论与证据

### 6.1 命令示例格式

命令或配置示例采用以下格式：

````markdown
**执行端：客户端**  
**适用范围：Linux NFS 客户端，内核 5.4+**

```bash
nfsstat -m
```

预期观察：确认协商出的 NFS 版本、`rsize`、`wsize`、传输协议和挂载语义。
````

### 6.2 事实与建议的区分

技术表述必须区分三类内容：

| 类型 | 写法 | 证据要求 |
| --- | --- | --- |
| 协议或内核事实 | “NFSv4.1 引入 session” | RFC、内核文档或发行版官方文档 |
| 环境观测结果 | “本实验中 WRITE 延迟升高” | 命令输出、指标、抓包或实验条件 |
| 工程建议 | “该场景建议使用 hard 挂载” | 适用条件、风险、替代方案与验证方法 |

不将某一发行版、内核版本或单次压测结果泛化为通用结论。

### 6.3 实验记录

需要复现的实验放入 `L7-practice`，文件名仍使用统一规范。实验文档必须记录：

- 拓扑、主机角色、OS 和内核版本；
- NFS 服务端与客户端版本、导出及挂载参数；
- 网络、存储和负载生成方式；
- 执行步骤、原始关键输出和观察指标；
- 预期结果、实际结果、差异解释及清理/回滚步骤。

不得记录真实生产密码、Kerberos keytab、IP 地址、客户名称、文件名或其他敏感数据；应使用脱敏占位符。

## 7. 文档状态

| 状态 | 含义 | 可否作为生产依据 |
| --- | --- | --- |
| 草稿 | 内容尚未完整或结论未校验 | 否 |
| 待验证 | 内容完整，但尚未在目标环境或可靠来源验证 | 否 |
| 已验证 | 原理、命令和版本边界均已有证据支持 | 可以，仍须结合目标环境评估 |
| 已归档 | 被新文档替代或只保留历史参考价值 | 否，必须指向替代文档 |

状态变更必须在“变更记录”中说明原因和证据来源。

## 8. 版本与变更记录

文档版本使用 `主版本.次版本.修订版本`：

| 变更类型 | 示例 | 版本规则 |
| --- | --- | --- |
| 结论、目录或适用边界发生不兼容变化 | 更正错误的 NFS 语义 | 主版本加一 |
| 新增完整章节、实验或支持的版本范围 | 新增 NFSv4.2 案例 | 次版本加一 |
| 勘误、措辞或链接修正 | 修正命令参数说明 | 修订版本加一 |

文末必须保留变更记录：

```markdown
## 变更记录

| 日期 | 版本 | 变更内容 | 证据或原因 |
| --- | --- | --- | --- |
| 2026-07-31 | 1.0.0 | 初始发布 | 建立 NFS 知识库治理基线 |
```

## 9. 链接与引用

- 内部引用使用相对 Markdown 链接，并使用文档编号作为链接文本。
- 外部事实优先引用 RFC、Linux 内核文档、NFS man pages、发行版官方文档和权威实现文档。
- 引用应标记用途，例如“协议定义”“参数语义”“版本兼容性”或“实现参考”。
- 外部链接不可用时，不删除原结论；应将状态调整为“待验证”并记录影响范围。

## 10. 发布检查清单

每份文档发布为“已验证”前，必须确认：

- [ ] 文件名、目录和编号符合第 2、3 节。
- [ ] 元数据完整，适用范围与版本边界明确。
- [ ] 原理、配置、验证、风险和排障路径齐全。
- [ ] 所有命令都已标明执行端，并说明预期观察结果。
- [ ] 高风险配置包含风险、限制与恢复措施。
- [ ] 结论已标明证据来源或实验条件。
- [ ] 内部链接有效，外部参考资料可追溯。
- [ ] 变更记录已更新，且未包含敏感信息。

## 11. 本规范的维护

本规范是知识库的治理基线。变更本规范时必须：

1. 说明变更动机、影响范围和迁移策略。
2. 增加本规范的版本号并更新变更记录。
3. 不批量重命名已发布文档；如确需迁移，保留旧路径说明或建立索引映射。
4. 在 `README.md` 中同步当前生效版本。
